Built 2026-11-04 for testing ball control. `Assets/Scenes/TestScene5_BallCourse.unity` is a copy of TestScene1_Ball_Camera, generated by `Assets/Scripts/Editor/BallCourseBuilder.cs` (menu **Tools > MiniCarGolf > Build Ball Course Scene**; re-runnable, constants at the top; assets in `Assets/BallCourse/`). Basic layout after a "roller coaster" mini-golf reference image: raised tee (0.6 m) → smooth ramp → flat spot reserved for a vertical loop (step 2, not built) → 90° right → back straight → 180° U-turn → return lane → 108 mm cup with an end wall. Floor and rails are swept along one centre line (no seams).

**Golf-ball setup (new scene only):** PlayerBall scaled to 4.27 cm, mass 0.0459, Continuous Dynamic, Interpolate, GolfBall physic material (friction 0.4, bounce 0.6); a 15 cm trigger SphereCollider on the ball as an easier click target; `Ball.ballSpeed` 0.6 (top shot ~3.9 m/s); Main Camera 2.5 m behind the follow pivot; GameZone/Cubes disabled. New runtime scripts: `GolfBallPhysics.cs` (maxAngularVelocity 1000, since the project default of 7 rad/s makes a small ball slide; solid-sphere inertia so the click trigger doesn't change spin) and `BallCupTrigger.cs` (logs "Ball holed").

**Tested:** ball rolls correctly; ramp is smooth (0.6 → 2.2 m/s); a ~0.5 m/s putt drops in and logs; a ~2 m/s ball lips out. Problems: `Physics.bounceThreshold` is 2 m/s (project-wide), so rail/wall hits below 2 m/s didn't bounce (ball stopped dead at the end wall). Fixed 2026-11-10 at the user's request ("a bit more bounce"): `GolfBallPhysics` sets bounceThreshold to 0.3 (serialized, tunable) in Awake and restores the old value in OnDestroy, so car scenes keep 2. Not yet tested (Unity MCP was disconnected). Still open: drag-based slowing gives a long slow crawl instead of a firm stop (constant rolling resistance proposed, not approved). Loop needs ~8.5 m/s, so it requires a higher start or more shot power.

The user made copies TestScene5_BallCourseB and TestScene5_BallCourseC (the builder only touches TestScene5_BallCourse). On 2026-11-15, in C only, the Main Camera was moved from 2.5 m to 1.533 m behind the pivot (FOV kept at 60): the same ball size on screen as FOV 60 → 39 (distance × tan(19.5°)/tan(30°), ~39% closer). The user then set FOV to 52.8 (kept 1.533 m). The ZoomIn scene was later renamed from C to `TestScene5_BallCourseZoomIn`; the user prefers keeping the 30° camera pitch.

**Occlusion handling (2026-11-16, ZoomIn scene only):** `Assets/Shaders/BallXRay.shader` (glowing lat/long globe + rim, drawn only where hidden via ZTest Greater; added as a 2nd material `BallXRay.mat` on PlayerBall) and `Assets/Shaders/SeeThroughRail.shader` (`RailSeeThrough.mat` on Rails/StartWall/EndWall: cyan wireframe window in rails between camera and ball). `Assets/Scripts/BallOcclusionHelper.cs` on Main Camera sends `_BallScreen` (viewport xy, eye depth, radius) in OnPreCull and clears it in OnPostRender. Bug found and fixed: the grid used all 3 world axes, so faces at whole-grid coordinates filled solid; now it skips the axis along the face normal. Tested in Play mode: works. Cost is light (one extra ball draw + a few ALU per rail pixel, alpha-tested). Then, at the user's request, the window became 40% see-through instead of a wireframe: pass 1 cuts the window out, pass 2 redraws only window pixels alpha-blended (`Window opacity`, 0 = see-through, 1 = solid); `Show wireframe grid` is a checkbox, now off; a thin cyan edge ring stays. Known harmless Inspector warning on PlayerBall: "more materials than submeshes" (the 2nd X-ray material); could switch the ball to XRaySilhouette to remove it.

**Car X-ray (2026-11-16):** `Assets/Scripts/XRaySilhouette.cs` on the `Hummer` prefab root (variant of Player Basic; used in TestScene3_Hammer, TestScene3_Terrian, TestScene4). It draws a pre-merged mesh `Assets/Scripts/FromHammer/Car/Hummer_XRay.asset` (65 parts / 85 sub-meshes → 1 mesh, ~30k tris; baked in the editor because Hummer_V2.fbx has Read/Write off, so runtime CombineMeshes would fail in builds) with `XRayMask.mat` (stencil pre-pass, `Assets/Shaders/XRayMask.shader`) + `CarXRay.mat` (BallXRay shader, grid off, stencil NotEqual) in `Assets/Shaders/Materials/`. 2 extra draws total. Same cyan as the ball on purpose: ball and car are the same game piece. Re-bake via right-click component > Bake X-ray mesh if the model changes. Hidden parts stack additively (internal parts visible) - a flat single-layer silhouette is possible if wanted.

**REPLACED 2026-11-17 (user request, after a Golf With Your Friends reference image): outline only, no see-through.** Hidden ball/car now show just a constant-width cyan outline ring (`Assets/Shaders/XRayOutline.shader`: inflate along normals in view space, `abs(P[1][1])` pixel scale, Cull Off, ZTest Greater, stencil NotEqual; `_OutlineWidth` px (3), `_DepthBias` "hidden threshold" m (ball 0.03, car 0.3) so the floor doesn't trigger a ring, `_UseSmoothNormals` toggle = keyword `_USESMOOTHNORMALS_ON` reading UV4). `XRayMask.shader` now ZTest Always + Cull Off (whole silhouette). `XRaySilhouette` fields: outlineMaterial (FormerlySerializedAs xrayMaterial), maskMaterial, bakedMesh; car bake writes smoothed normals to UV4. Materials: BallXRay.mat (ref 2) + BallXRayMask.mat, CarXRay.mat (ref 1, keyword on) + XRayMask.mat. Deleted: OcclusionWindow.cs, SeeThroughRail.shader, BallXRay.shader, RailSeeThrough.mat (all recoverable from git commit f733628). Rails back to Rail.mat; TestCourse materials back to Standard with their builder colours. Tested 2026-11-17: hidden ball/car → ring; visible against a wall → nothing. Car re-tested after the last shader edits: OK. Everything below about the see-through window is history.

**Unified (2026-11-16, at the user's request):** the ball now also uses `XRaySilhouette` (2nd material removed, so the "more materials than submeshes" warning is gone). Ball uses stencil ref 2 (`BallXRay.mat` + `Assets/Shaders/Materials/BallXRayMask.mat`), car ref 1 (`CarXRay.mat` + `XRayMask.mat`), so they never block each other. `XRaySilhouette` has **See Through Radius** (world metres; ball 0.12, Hummer prefab 1.0) - the user asked for this field. `BallOcclusionHelper` was renamed to **`OcclusionWindow`** (same .meta GUID, so scene references survived). It picks `Target` (or the first active XRaySilhouette), and opens the window ONLY when the piece is actually hidden: 5 rays from the camera to points inside the piece's solid colliders, hidden if ≥ `hiddenFraction` (0.5) are blocked; the window fades over `fadeTime` (0.15 s). `Target` is public for the future ball↔car switch. On the camera in TestScene5_BallCourseZoomIn and TestScene4_TerrianClaude. The TestCourse obstacle materials (Curb, Ramp, Jump, Washboard, DeadEnd) were switched to the SeeThroughRail shader so the car gets the window too (terrain can't). Tested: hidden ball/car → window; ball/car against a wall but visible → nothing.
